# 公会系统 (guild)

> Entry id: `guild`
> Type: system
> Last updated: 2026-05-10

> 这是一个**写满的 entry 示例**,展示 MD 字典的写法。内容是中性的虚构例子,供参考结构。

## 是什么

公会系统是玩家之间的中型组织单位,提供成员管理、共享仓库、集体活动和资源池。它是社交系统的核心组成部分,与邮件、日志等模块紧密耦合。

公会以 `Guild` 聚合根承载完整生命周期数据,通过 `GuildManager` 集中处理业务逻辑。

公会创建后即落库;解散时数据保留一段时间供回滚,过期后归档。

## 核心数据

- `Guild`:公会聚合根,包含信息、成员、仓库、日志等所有子数据
- `GuildInfoData`:公会基础信息(id、名字、等级、创建时间)
- `GuildMembersData`:成员集合
- `GuildMemberData`:单个成员(playerId、职位、加入时间)
- `GuildStoreData`:公会仓库

## 关键约定

### 持久化

- **修改 `Guild.storeData` 必须调 `saveToDB()`**:否则下次重启数据丢失
- **修改成员列表必须 `saveToDB()`**:成员变化是高频操作,注意批量写入避免 N+1
- **`Player.guildId` 修改必须 `saveToDB()` + 通知公会成员**:单边写入会导致公会和玩家两边数据不一致

### 权限

- **会长退会必须先转移会长权限**:直接退会会导致公会无主,业务层应拒绝
- **职位权限校验集中在职位枚举类**:避免业务层散落 magic number

### 业务规则

- **成员上限**:受公会等级限制,配置在等级表的 maxMember 列
- **公会名长度**:有上限(前后端都校验)

## 典型场景

什么样的需求 AI 应该来这个 entry:

- 加成员、踢成员、转会长、修改职位
- 公会等级提升、经验计算、捐献逻辑
- 公会仓库的上架、审核、领取
- 公会改名、公会公告

## 踩坑历史

- **2026-03**: 公会拍卖结束未触发邮件 → 在拍卖结束回调里显式调发邮件方法,不依赖事件总线(事件总线在不稳定场景下可能丢失)
- **2026-02**: 退会未清理 `Player.guildId` → 在 `removeMember()` 末尾显式清 guildId + saveToDB
- **2025-12**: 公会仓库击发奖励未给所有参与者 → 修改奖励发放从单点改为遍历参与者集合

## 设计要点

- **为什么 `Guild` 用聚合根而不是分散的 Manager**:早期分散管理(GuildInfoManager + GuildMemberManager + ...)跨业务调用频繁导致死锁。重构为聚合根后所有操作集中,加锁简单且性能更好。
